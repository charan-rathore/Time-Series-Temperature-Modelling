## Findings, with measurable evidence

1. The shipped 0.107°C and 0.221°C ensemble RMSE claims are invalid: `scripts/train_models.py` fitted the Ridge stacker to `test_df` predictions and `test_df` actuals, then scored a training row. This is answer leakage, not test performance. The public site currently displays stored results without models or observations. This patch disables the contaminated ensemble fit and artifact loading until genuine out-of-fold training and an untouched evaluation are built. SARIMA, LightGBM and TFT model training/serving are likewise disabled pending corrected forecast-origin/target alignment, issue-time covariate provenance, and a walk-forward evaluator. Their historical scores cannot be endorsed.
2. A fresh archive fetch for June 2-July 10 produced 39 same-date 21:00 archive temperatures. `python scripts/audit_observations.py --offline-raw data/raw/open_meteo_historical_2024-06-02_2024-07-10.json` joins 39 legacy dates. A fixed offset trained on the first 27 paired days is +4.722°C; on the last 12 untouched dates same-time archive MAE is 4.217°C and bias-adjusted same-time MAE is 1.287°C. This proves a retrospective archive/legacy offset for that span, NOT a forecast win; the archive's same-day value was unavailable at issuance and the legacy sensor location is unverified.
3. Open-Meteo Previous Runs API (https://previous-runs-api.open-meteo.com/v1/forecast ; docs https://open-meteo.com/en/docs/previous-runs-api) returned 24/48/72-hour-lead 21:00 local forecasts for all 40 legacy dates. Requested coordinates were 12.9716, 77.5946, but the API returned grid coordinates 12.970123, 77.56364 at 910 m elevation, about 3.3 km west. This is a grid estimate, not a reading at the sensor itself. `python scripts/backtest_open_meteo_previous_runs.py` reports MAE 3.900/3.795/3.820°C and RMSE 4.167/4.055/4.137°C for Day 1/2/3 respectively; all are biased cool against unverified legacy records. Unlike the same-time archive, these are genuine fixed-lead historical forecasts, but the legacy thermometer/site and exact daily observation time are not authenticated. No ThermoSense model forecasts from that period were verified, so no head-to-head superiority claim is possible.
4. A local experimental 7-observation rolling offset built only from rows dated before each nominal forecast issue improved the archived Open-Meteo comparison on the same 30 held-out legacy dates: Day-1 raw/corrected MAE 4.157/1.336°C, Day-2 3.977/1.302°C, Day-3 3.963/1.420°C. `python scripts/evaluate_bias_correction.py` fetches Previous Runs afresh to reproduce this; the optional `--offline-raw` flag accepts a previously saved response and reproduces this without current or future target readings in the adjustment. This tests the promise that a site-specific offset can improve past forecasts, but is NOT a live DHT22 result and cannot verify coordinates, siting, or legacy 21:00 timestamps. It also cannot establish a generalized advantage over other weather vendors.
5. `python scripts/backtest_legacy.py` produces real time-ordered, future-label-free simple baseline results on the 40-day legacy series. With a 20-day warmup: persistence versus trailing 7-observation mean MAE is Day 1: 1.200/1.336°C (20 targets), Day 2: 1.737/1.323°C (19), Day 3: 1.611/1.190°C (18). These are simple baselines, not the ThermoSense trained model or a commercial API comparison.
6. The actual local backfill ran and produced 40 processed days, but lag/rolling features left only 26 usable days. With a 14-day validation and 14-day test window, the original training script had an empty validation slice and failed. A permissive local retry with only 9 training/3 validation days yielded LightGBM Day-1 RMSE 2.087°C, clearly insufficient evidence for model superiority. That exploratory retry is not a publishable performance figure or an endorsed experiment. Training now refuses a hyperlocal claim without 60 DHT22-tagged feature rows and 90 total complete days.
7. The Pi reader previously switched to simulated numbers when its sensor driver was missing; those could enter the uploader. The local patch moves to Adafruit CircuitPython DHT/Blinka, refuses real-mode startup without that driver, and requires `--simulate` for fake readings. Physical Pi driver compatibility is unverified. The ingestion endpoint rejects simulated and out-of-range values. Pi UTC timestamps are converted to local 21:00 before choosing the daily actual. The formerly public Pi HTTP server now binds to loopback.
8. The uploader previously marked all readings synced if the server stored one daily aggregate from 100 readings. The API now returns an explicit count of processed inputs, and the uploader retains a partial or failed batch instead of silently marking it all synced. Upload, feedback and pipeline writes require a durable host; sensor uploads, manual feedback and pipeline writes require a configured key. The stateless Vercel deployment returns 503 rather than claiming a write succeeded.
9. No physical Raspberry Pi/DHT transaction has been observed. The repo's legacy CSV does not document the device, site placement, calibration, or exact issue-time commercial forecast snapshots. Those are prerequisites to validating the promised hyperlocal product and leaderboard. A local ingestion bridge now merges DHT22-tagged daily actuals into the feature source on backfill/daily update; it needs an actual persistent deployment and sensor to be tested end to end.

## What would make the headline claim real

Provide the timestamped Pi readings database or export, verified site coordinates and placement, and evidence of which forecasts were generated before each observation. Run an independently scheduled collector that stores immutable forecast snapshots for Open-Meteo and each named vendor at the same time, target, and location. Collect enough paired days at the exact 21:00 local target, then fit only on earlier days; compare the untouched rolling forecast errors to persistence and each vendor on matched dates, with intervals and honest sample sizes. No commercial superiority can be asserted from the current sources.

## How the physical path works

The DHT22 measures temperature and relative humidity inside one small package. Its DATA pin carries a timed digital pulse train, not an analog voltage proportional to temperature. The Pi supplies 3.3V and ground, and uses GPIO4 (physical pin 7) to request and decode a reading. A pull-up between DATA and 3.3V keeps the line high when neither side drives it; a module may already have one. Connect VCC to physical pin 1 (3.3V), DATA to pin 7, GND to pin 9. Do not send 5V data levels to the Pi's 3.3V GPIO; check the exact module pinout before power. Allow at least two seconds between DHT22 reads.

On the Pi, `sensor_daemon.py` tries the GPIO read, validates plausible temperature/humidity, timestamps it in UTC and writes it into local SQLite every five minutes. `uploader.py` queries unsynced rows over localhost and posts batches with an API key to a persistent server; only fully acknowledged rows are marked synced. The server validates an API key and source tag, but it cannot physically attest the device. It converts timestamps to the site's local time, chooses a reading within 30 minutes of 9 PM and stores that day's actual. Backfill/daily update overlays that actual on the weather archive before building features. Training requires a long enough series of actual sensor-tagged observations; only then can you test forecast errors on later days. The public Vercel page has none of these observed readings at review time, so its live device loop remains unverified.

## Validation and limits

Local suite: 118 passed, two third-party/scipy warnings. React production build succeeds. The six original failures were four brittle raw-file test paths, one stale date-window fixture, and one stale sensor-history date filter. The browser feedback/training controls are disabled on every host until a secure key-bearing server-side workflow and prospective model evaluation exist. Physical sensor behavior is unverified. The changed UI was inspected in a local browser at desktop width; mobile rendering has not been checked. This is a review branch, not a deployed or hardware-certified release.
